# Contributing

Thank you for helping. This is the Python SDK for the Cru Trading API; the API itself, its
OpenAPI spec and the code generator live in Cru's own repository.

## The layout

```text
cru-api-python/
├── .github/            CI and release workflows, Dependabot, issue and pull request templates
├── api/                openapi.yaml: the copy of the spec the generated code comes from
├── src/cruworldwine/   the package: the hand-written core, and the generated models/ and resources/
├── tests/
│   ├── unit/           every test that runs on mocks alone; their coverage must stay at 90% or more
│   └── integration/    replays of captured API answers, and a read-only live smoke test
├── examples/           scripts to run against the API, type-checked with the package
├── docs/               the guides, including architecture.md: how the SDK is built
├── hack/               scripts behind the Makefile: regenerating, verifying, lowest-version tests
├── Makefile            every task, the same ones CI runs
└── pyproject.toml, uv.lock, README.md, CHANGELOG.md, CONTRIBUTING.md, SECURITY.md, LICENSE
```

## Generated and hand-written code

Part of this repository is generated from the API's OpenAPI spec and is **never edited by hand**:

- `src/cruworldwine/models/`: one module of models per resource;
- `src/cruworldwine/resources/`: one module per resource, with a class for `Cru` and one for
  `AsyncCru`;
- the method table in `README.md`, between the `sdkgen:methods` markers;
- `api/openapi.yaml`, the copy of the spec they were generated from.

Each generated file starts with `# Code generated by sdkgen ... DO NOT EDIT.` A change to the API
surface (a new endpoint, parameter, field or description) is made to the spec in Cru's API
repository and regenerated from there, so please open an issue for it rather than a pull request.
Maintainers regenerate with `make generate` and check with `make verify-generated`, both with
`CRU_API_REPO` set to the API repository's web-root. The generator writes code that already passes
`ruff format`, `ruff check` and `mypy --strict`, and two runs give byte-identical output.

Everything else is hand-written and takes normal pull requests: the core (`_base_client.py`,
`_client.py` and the other underscored modules), tests, examples, documentation and CI.
[docs/architecture.md](docs/architecture.md) says which file to change for what.

## Setting up

You need [uv](https://docs.astral.sh/uv/) and `make`. uv installs the Python versions and the
tools the project pins in `uv.lock`:

```sh
git clone https://github.com/cruworldwine/cru-api-python
cd cru-api-python
make install
```

## The Makefile

`make` alone lists the targets. Every pull request must pass `make ci`, which runs what CI runs.

| Target | What it does |
|---|---|
| `make install` | Install the package and every development tool, as `uv.lock` pins them. |
| `make fmt` | Format the code and apply ruff's safe fixes. |
| `make lint` | `ruff check` and `ruff format --check`. |
| `make typecheck` | `mypy --strict` on `src/` and `examples/`. |
| `make test` | The unit tests, with branch coverage of at least 90%. |
| `make test-lowest` | The unit tests on Python 3.9 with httpx and the test tools at their lowest allowed versions. |
| `make integration` | Replay captured API answers through `Cru` and `AsyncCru`; needs `CRU_CAPTURES`. |
| `make live` | A read-only smoke test against the live API; needs credentials in the environment. |
| `make build` | Build the sdist and wheel and check them with `twine check --strict`. |
| `make generate`, `make verify-generated` | Regenerate the generated code, or check it is up to date; need `CRU_API_REPO`. |
| `make clean` | Remove build outputs and caches. |
| `make ci` | `lint`, `typecheck`, `test`, `test-lowest` and `build`. |

The unit tests need no credentials and make no network calls. CI runs them on every supported
Python; to run them on another one locally, set `UV_PYTHON`, for example
`UV_PYTHON=3.15 make test`. `HYPOTHESIS_PROFILE=ci` runs the property tests with as many examples
as CI does, and `PYTEST_ARGS` passes arguments to pytest: `make test PYTEST_ARGS='-k refresh'`.

`make integration` needs `CRU_CAPTURES` set to a run of the API repository's `spec_capture.php`.
Those captures hold customer data: they are read where they are and must never be copied into this
repository. `make live` calls the real API with the credential in your environment, and only reads.

## Commits and pull requests

- Keep a pull request to one change, with tests that fail without it, for `Cru` and `AsyncCru`
  alike.
- Write commit messages in the imperative, with a short subject line and a body that says why.
- Add a line to `CHANGELOG.md` under `## [Unreleased]`, in the section that fits: Added, Changed,
  Deprecated, Removed, Fixed or Security. A change to the public API goes under Changed or Removed
  and says what users must do.
- Keep the public API backwards-compatible within a minor release. Names that start with an
  underscore are internal.
- Never put credentials, tokens or customer data in code, tests, issues or pull requests.

## Releasing

Releases are cut from `main` by a maintainer:

1. Bump the version in `pyproject.toml` and `src/cruworldwine/_version.py`.
2. In `CHANGELOG.md`, rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, open a new empty
   `## [Unreleased]` above it, and update the links at the bottom.
3. Merge that to `main`, then tag the merge commit with an annotated tag (`-s` instead of `-a`
   signs it) and push the tag:

   ```sh
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```

The `Release` workflow then runs every check, confirms the tag matches the package version and
that the changelog has a section for it, builds the distributions with `make build` and attests
their build provenance, publishes them to PyPI by Trusted Publishing (no API tokens), and creates
the GitHub Release with that changelog section as its notes and the distributions attached.
Publishing waits for approval on the `pypi` environment when the repository requires it.
