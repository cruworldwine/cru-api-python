# Contributing

Thank you for helping. This is the Python SDK for the Cru Trading API; the API itself, its
OpenAPI spec and the code generator live in Cru's own repository.

## Generated and hand-written code

Part of this repository is generated from the API's OpenAPI spec and is **never edited by hand**:

- `src/cruworldwine/models/`: one module of models per resource;
- `src/cruworldwine/resources/`: one module per resource, with a class for `Cru` and one for
  `AsyncCru`;
- the method table in `README.md`, between the `sdkgen:methods` markers;
- `spec/openapi.yaml`, the copy of the spec they were generated from.

Each generated file starts with `# Code generated by sdkgen ... DO NOT EDIT.` A change to the API
surface (a new endpoint, parameter, field or description) is made to the spec in Cru's API
repository and regenerated from there, so please open an issue for it rather than a pull request.
The generator writes code that already passes `ruff format`, `ruff check` and `mypy --strict`, and
two runs give byte-identical output.

Everything else is hand-written and takes normal pull requests: the clients and transport
(`_base_client.py`, `_client.py`), errors, models' base class, pages and writes, logging, tests,
examples, documentation and CI.

## Setting up

You need [uv](https://docs.astral.sh/uv/). It installs the Python versions and tools the project
pins in `uv.lock`:

```sh
git clone https://github.com/cruworldwine/cru-api-python
cd cru-api-python
uv sync
```

## Checks

Every pull request must pass the same checks CI runs:

```sh
uv run ruff check .              # lint
uv run ruff format --check .     # formatting (uv run ruff format . to fix)
uv run mypy                      # strict type check of src/ and examples/
uv run pytest --cov              # tests, with at least 90% coverage
```

The tests need no credentials and make no network calls. Run them on the oldest and newest
supported Pythons before you push:

```sh
uv run --isolated --python 3.9 pytest
uv run --isolated --python 3.15 pytest
```

`HYPOTHESIS_PROFILE=ci` runs the property tests with as many examples as CI does.
`CRU_CAPTURES=<a spec_capture.php run>` also replays real API answers through both clients; those
captures hold customer data and must never be copied into this repository.

To build and check the distributions:

```sh
uv build
uv run twine check --strict dist/*
```

## Commits and pull requests

- Keep a pull request to one change, with tests that fail without it.
- Write commit messages in the imperative, with a short subject line and a body that says why.
- Add a line to `CHANGELOG.md` under `## [Unreleased]`, in the section that fits: Added, Changed,
  Deprecated, Removed, Fixed or Security. A change to the public API goes under Changed or Removed
  and says what users must do.
- Keep the public API backwards-compatible within a minor release. Names that start with an
  underscore are internal.
- Never put credentials, tokens or customer data in code, tests, issues or pull requests.

## Releasing

Releases are cut from `main` by a maintainer:

1. Bump the version in `pyproject.toml` and `src/cruworldwine/_version.py`.
2. In `CHANGELOG.md`, rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, open a new empty
   `## [Unreleased]` above it, and update the links at the bottom.
3. Merge that to `main`, then tag the merge commit with an annotated tag (`-s` instead of `-a`
   signs it) and push the tag:

   ```sh
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```

The `Release` workflow then runs every check, confirms the tag matches the package version and
that the changelog has a section for it, builds the distributions with build provenance
attestations, publishes them to PyPI by Trusted Publishing (no API tokens), and creates the GitHub
Release with that changelog section as its notes and the distributions attached. Publishing waits
for approval on the `pypi` environment when the repository requires it.
